## 三、自审（5 视角对抗式 + 变异测试）新发现，已修

1. **R4 只修了一半**（P1）——`/player/status` 有**两处**压制规则（缓存命中 / 未命中），上一轮只改了后者。4 秒缓存窗口内 bug 原样存在，且那两条"证明修复"的测试恰好都走缓存路径，回退后照样通过。
2. **`/mina/stop` 绕过 PlaylistManager**——与 R1 中 `/mina/pause` 完全同款，当时只修了 pause。
3. **定时任务丢弃 `stop()` 返回值**——睡眠定时器会在音箱仍在播放时记「停止播放成功」。
4. **`playerPause`/`playerStop` 只判 `!== null`**——这是最底层的问题：整条布尔链建立在一个**不校验设备返回码**的判定上，而 `playURL` 一直用的是 `isDeviceResultOK`。设备明确拒绝时上层仍报成功。
5. **两处安全改动无任何测试**（`2bed9e4`）——Webhook 投递前重新校验、二维码轮询缓存剥离凭据。

## 四、待处理（暂停在此）

### 已确认、优先级从高到低

- **P2 · 音乐页三个浏览器播放入口未接暂停音箱**
  `9776168` 建立的不变量是「任何浏览器播放入口都要先暂停音箱」，但只接进了 `player.js` 的两处。从音乐页以 target=browser 起播时，两端仍会同时出声，且没有提示。
  修复思路：把 `pauseSpeakerForBrowserPlayback()` 提到共享模块，music 页三处入口统一调用；沿用已有的失败提示。

- **P2 · 新配置项没有写入路径**
  `song_transition_offset` / `prefetch_next_song` 只有默认值和读取，`handlers/config.ts` 未纳入白名单，GET 也不返回 → **用户无法关闭预取**。
  修复思路：在 config handler 的写入白名单补两项（偏移做 ±30 收敛、预取做布尔校验），并确认 GET 返回。

- **P2 · `getCurrentSong()` 原样返回 `PlayerSong`**
  七个 handler 响应会因此带出 `source_data` / `lyric_text`。`getStatus()` 的投影是干净的，但这条路径不是。
  修复思路：加一层投影函数，与 `getStatus()` 用同一份字段白名单。

- **P3 · 随机模式下预取/歌词预填可能取错曲目**
  `getNextIndex()` 在 random 模式有副作用（写 `randomPlayed`），被 `prefetchNextSong()` 和 `fillLyricsAround()` 当作纯函数"看一眼下一首"来用。
  修复思路：抽一个无副作用的 `peekNextIndex()`，两处 peek 改用它。

- **P3 · 状态轮询无请求序号防护**
  封面和歌词都加了 `requestId` 守卫，但驱动整个 UI 的状态轮询没有。5 秒轮询的响应可能在用户暂停之后才落地，把界面重新画成 playing。
  修复思路：与封面/歌词同款的单调 id 守卫。

- **P3 · `pause()` 无来源状态守卫**
  空闲管理器调用后也会翻成 `paused`，随后 `/player/toggle` 会优先走 `resumePlayback()` 而非 `play()`。

### 需要真实设备验证，不宜凭推断修改

- **网易云封面带宽**：`picUrl` 是原图，实测存在 3648×3648 / 595 KB，而列表只显示 44px。正确做法是追加 `?param=WxH` 当上限（网易云的 param 只缩不放）。**落地前必须先抓真实 `p*.music.126.net` 封面验证**：(a) 3648 原图会被压到目标尺寸；(b) 500 原图不会被拉伸。
- **发现页「加载榜单」返回 `source_id is required`**：已确认**不是**本轮回归（`rankings.js` 的请求构造改前改后逐字节相同，且 `ranking-platform` 实测有值）。属后端契约或音源能力问题，需单独排查。
- **预取依赖宿主 `?prefetch=1`**：已实测该宿主返回 202 空响应，但这是未文档化的约定，换宿主可能失效。

### 已评估、决定不改

- 索引模糊匹配的等价优化没有"证伪测试"——这是**正确**的。等价优化按定义不改变行为，任何行为测试都无法区分回退前后；已有的 5 条是等价性护栏。等价性另由 40 万组随机差分验证（mismatch = 0）。
- `main.jsc` 占压缩后包体 87%，是体积唯一大头，需 esbuild 层面评估，超出本次范围。
- 遗留 handler 用 HTTP 200 + `{success:false}` 表达校验错误——不符合 REST 惯例，但这是整个 `/api/miot` 家族的一致契约，前端读的是 `success` 而非状态码，改动属破坏性 API 变更。

## 五、方法论备忘（这轮反复踩到的坑）

1. **绿灯不等于有效。** 本轮至少 6 条测试在写完时是通过的，但其实什么都没断言：夹具缺必填字段、构造参数顺序写反、状态值不在终态集合、断言点选在内部方法而非可观测输出。全部只在**反证**时才暴露。

2. **反证本身会失效。** 出现过 3 次「破坏后测试仍通过」，其中 2 次是**破坏根本没生效**（正则没匹配上，源码原封未动）。因此流程必须是：改 → **验证改动确实落到文件里** → 跑测试 → 确认失败原因是预期的那个。

3. **检测脚本也会说谎。** 变异测试第一版用 `--silent` 跑 vitest 又去 grep `"Tests N failed"`，而 `--silent` 恰好抑制了这行，于是每次真实失败都被读成"无失败"，产出一份 13 个文件的假缺口清单。改用退出码后缩到 4 个。

4. **修一处必查同族。** R1/R3/R4 三轮外部 review 和本次自审，指向的都是同一形态：把修复打在被点名的那个调用点上，而它旁边语义相同的兄弟原封不动。现在的做法是先枚举同族调用点，再逐个判断语义是否相同。
