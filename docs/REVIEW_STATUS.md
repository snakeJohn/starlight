1. **R4 只修了一半**（P1）——`/player/status` 有**两处**压制规则（缓存命中 / 未命中），上一轮只改了后者。4 秒缓存窗口内 bug 原样存在，且那两条"证明修复"的测试恰好都走缓存路径，回退后照样通过。
2. **`/mina/stop` 绕过 PlaylistManager**——与 R1 中 `/mina/pause` 完全同款，当时只修了 pause。
3. **定时任务丢弃 `stop()` 返回值**——睡眠定时器会在音箱仍在播放时记「停止播放成功」。
4. **`playerPause`/`playerStop` 只判 `!== null`**——这是最底层的问题：整条布尔链建立在一个**不校验设备返回码**的判定上，而 `playURL` 一直用的是 `isDeviceResultOK`。设备明确拒绝时上层仍报成功。
5. **两处安全改动无任何测试**（`2bed9e4`）——Webhook 投递前重新校验、二维码轮询缓存剥离凭据。

## 五、方法论备忘（这轮反复踩到的坑）

1. **绿灯不等于有效。** 本轮至少 6 条测试在写完时是通过的，但其实什么都没断言：夹具缺必填字段、构造参数顺序写反、状态值不在终态集合、断言点选在内部方法而非可观测输出。全部只在**反证**时才暴露。

2. **反证本身会失效。** 出现过 3 次「破坏后测试仍通过」，其中 2 次是**破坏根本没生效**（正则没匹配上，源码原封未动）。因此流程必须是：改 → **验证改动确实落到文件里** → 跑测试 → 确认失败原因是预期的那个。

3. **检测脚本也会说谎。** 变异测试第一版用 `--silent` 跑 vitest 又去 grep `"Tests N failed"`，而 `--silent` 恰好抑制了这行，于是每次真实失败都被读成"无失败"，产出一份 13 个文件的假缺口清单。改用退出码后缩到 4 个。

4. **修一处必查同族。** R1/R3/R4 三轮外部 review 和本次自审，指向的都是同一形态：把修复打在被点名的那个调用点上，而它旁边语义相同的兄弟原封不动。现在的做法是先枚举同族调用点，再逐个判断语义是否相同。

5. **能把不变量放进唯一入口，就别靠调用点自觉。** 「浏览器开播必须先停音箱」这条，靠每个入口自己记得调用 → 音乐页三处全漏。改为放进 `playBrowserQueue()` 内部后，新增入口自动获得该保证。同理 `current_song` 的字段白名单抽成共享投影，两处不会再各改各的。这比「记得每处都改」可靠。

6. **反证失败时，先怀疑自己的前提，而不是只怀疑测试写法。** random 模式那条，我最初断言「播放序列覆盖会被破坏」，反证不失败。原因不是测试写得差，而是**前提本身错了**——`randomPlayed.add(currentIndex)` 是幂等的，覆盖并不会被破坏。真实危害是「前瞻拿到的和真正会播的不是同一首」。换成观察这个之后，反证立刻输出 `实际补了 第1首/第3首`。
